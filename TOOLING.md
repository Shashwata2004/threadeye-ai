### Upstream provenance and maintenance

Spec Kit source: [github/spec-kit v1.4.3](https://github.com/github/spec-kit/tree/v1.4.3),
archive commit prefix `d274613`. The official source was built in an isolated
temporary Python environment. Its CLI initialized a temporary project using:

```sh
specify init /tmp/threadeye-ai-dlc/scaffold --integration claude --script sh --ignore-agent-tools --non-interactive
```

The generated `.specify/` and Claude skills were copied into this repository;
the placeholder constitution was replaced with project principles. The upstream
MIT license is retained in `.specify/UPSTREAM-LICENSE`. The temporary environment
is not an application dependency or a portable installation of the CLI.

To install the same CLI for future maintenance in a dedicated environment:

```sh
python3 -m venv /tmp/threadeye-speckit-venv
/tmp/threadeye-speckit-venv/bin/pip install 'git+https://github.com/github/spec-kit.git@v1.4.3'
```

Start Claude Code from this repository to discover `/prepare-defect-review-data`
and the upstream `/speckit-*` skills. The first feature folder is only a draft;
it does not select a feature branch automatically. Before continuing that draft,
set `SPECIFY_FEATURE_DIRECTORY=specs/001-reviewed-defect-manifest` and
`SPECIFY_FEATURE=001-reviewed-defect-manifest` in the shell that launches Claude.
The directory selects this draft; the second variable supplies its feature name.
Do not run the implement skill merely to complete setup. Follow the requested
scope for subsequent work.

No tests, validators, model training, production changes, publishing or deployment
were performed for this setup request. Framework initialization is the only CLI
workflow executed. Submission descriptions should say **setup added** until there
is evidence of an actual feature workflow and skill execution. No point increase
or judge acceptance is established by these files.

## Operational visualizations — 2026-11-20

Four open-source plotting libraries are integrated into existing app pages:

| Library | Page | Actual use |
|---|---|---|
| Recharts | Dashboard (`/`) | Donut of today's finalized PASS / BORDERLINE / FAIL roll verdicts |
| Chart.js | Mill scorecards (`/suppliers`) | Monthly points-per-100-sq-yd trend, gaps for missing months, and the existing 40-point scorecard reference |
| Apache ECharts | Inspection report (`/inspections/[id]`) | Confirmed defect counts by class and yard-position bin; rejected, pending and nondefect entries excluded |
| Plotly.js (basic bundle) | Benchmark (`/benchmark`) | Dataset localization/correct-class recall comparison and selectable per-class precision/recall bars |

Dependencies and resolved versions are recorded in `frontend/package.json` and
`frontend/pnpm-lock.yaml`. Chart components live in `frontend/src/components/charts/`
and load on the client only for the corresponding page. ECharts imports the
heatmap/SVG modules; Plotly uses its basic bundle. No CDN or external plotting
service is required. Existing custom React/SVG cutting maps remain in use.

All plots use existing API data, support English/Bangla and light/dark themes,
and provide exact-value tables and empty states. Missing benchmark values are
not plotted as zero; dataset precision is not available in the current report.
The all-mill monthly trend is weighted by each month's actual inspected rolls.
The heatmap counts each confirmed defect once at its center; it does not
represent defect size, scoring or cutting instructions.

Specification and acceptance checklist: `specs/003-operational-charts/`.
Browser checks: `frontend/e2e/visualizations.spec.ts`, using isolated API fixtures
rather than writing to a live factory or cloud database. These plots introduce
no new model-performance or factory-impact measurements.

Validation: `pnpm check` (locale parity, ESLint, TypeScript) and `pnpm build`
passed. Against the local production build, the following browser command passed
all 18 tests, including English/Bangla, both themes, mobile chart widths, empty
states, monthly weighting, null values, confirmed-only heatmap counts, cutting
overlays, saved decisions and permission notices:

```sh
E2E_BASE_URL=http://127.0.0.1:3100 pnpm exec playwright test \
  e2e/visualizations.spec.ts e2e/cutting-map.spec.ts \
  e2e/cutting-policy-decision.spec.ts e2e/permissions.spec.ts --workers=1
```


## LangGraph companion workflow — 2026-11-20

The evidence companion now has an opt-in LangGraph 1.2.24 implementation in
`threadeye-evidence-assistant/src/threadeye_evidence/answering/workflow.py`, selected
by `answer-evidence --orchestration langgraph`. A conditional graph makes one
keyword-only recovery attempt after an identified vector backend failure. The
same authorization, sufficiency and citation checks run on both attempts; output
records framework identity, attempt outcomes and degraded-mode disclosure.

An isolated temporary environment installed the real `agentic` extra. Eight graph
tests passed; answering/retrieval regressions added 40 passing tests, with nine
database integration tests skipped. CLI help also exposed the new selection.
See the companion README for exact commands. No live database integration,
main-app deployment, LLM generation or autonomous QC action is claimed.

Submission wording for **Agentic Frameworks Used → LangGraph**:

> LangGraph orchestrates an opt-in, read-only evidence-recovery workflow in our
> Evidence Assistant companion CLI. It conditionally retries vector-backend
> failures with keyword retrieval, preserves authorization and citation checks,
> and exposes a bounded execution trace. Answers remain deterministic extraction;
> this integration does not use a generative LLM.

This feature is specified in `specs/002-evidence-recovery-workflow/`. Its completed
implementation and tests are separate from the earlier setup-only manifest draft.
